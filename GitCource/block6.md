# Работа в команде
## Работа над MR/PR
__MR/PR - Запрос на слияние. Один MR - это атомарный МР который решает какую то 1 задачу. Ненадо смешивать.__

## Code review - Best practise
__Зачем нужен код ревью?__
1) Разработчик пониманием какие изменения были и знает как обновлял проект
2) Проблема найденная на код ревью не наносит много деменджа в отличи от пропущенного бага
3) Поддерживает единый стиль кода

__Делай небольшие МРы чтобы легче проверить было. Проверяй сам МР - бывает что то находится. При ревью оцениваешь код, а не человека. Если есть разногласия можно созвониться. К мелочам тоже не придерайся.__

## Теги
__Теги указывают на конкретные коммиты. Обычно ими помечают релизы. Теги не изменить.__
__Есть 2 вида тегов:__
1) Легковесные - просто имя для коммита (Пример git tag v0.9.0 abc123def)
2) Аннотированные - Тег с описанием (Пример git tag -a v1.0.0 -m "First stable release")

__Обычно ставят версии так: Major.minor.patch - Серьезное изменение.Новая функциональность. Незначительная правка__

__Работа с тегами__
1) git tag - выводит список всех тегов
2) git tag -l "v1.*" - найти тег по шаблону
3) git show tag 1.0.0 - Показать инфу о теге
4) git push origin 1.0.0 - Отправить конкретынй тег(коммит котоырй под этим тегом)
5) git push origin --tags - Отправить все теги
6) git push origin --follow-tags - Отправить теги с описанием
7) git tag -d 1.0.0 - Удалить конкретный тег
8) git push origin --delete 1.0.0 - Удалить тег на сервере

## Стратегия ветвления

__Git Flow - Подход к ветвлению__
__Есть стабильная ветка и туда вливается только новая версия готового стабильного продукта (master/main)__
__Есть develop ветка - это версия продукта в которой сейчас идет разработка. От нее создаются фича ветки для разработки фичей и вливается в develop. Перед релизом develop вливается в main/master.__
__Так есть Hotfix ветки. Ветки для фикса хотфикс багов__
__Есть ветки названные в честь задачи__

__Есть упрощенных подход GitHub flow. Есть основная ветка master/main и ветки которые от нее идет типо fix/feature и тд. Упрощение для команд у которых непрерывное развертывание. То есть команды где могут быть несколько релизов в день.__

__Есть подход Trunk-based development - Работа идет сразу в ветке main или в очень короткоживущих фича ветках, которые вливаются в основную в течении дня.__
