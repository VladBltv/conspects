# Автоматизация и интеграция
## CI/CD
__Сервисы хостинги могут предоставлять возможности работы с CI/CD и получается что в этих сервисах уже идет работа не только изолированно с Git, но и работа с процессами развертывания, проверками и тд. Проекты типо Gitlab CI, Githab Actions, Jenkins позволяют выполнять CI/CD пайплайн на триггерные действия с git__
__CI/CD это по сути автоматизация процессов разработки__
__Автоматизация снижает риски человеческого фактора и существенно снижает время работы. Все происходит автоматически__
__В современно понимании CI/CD формирует как Configurations as Code - все описывается в файлах и вызывается автоматически. Примеры файлов:__
1) Gitlab - gitlab-ci.yml
2) GitHub - workflows/ci.yml
3) Jenkins - jenkinsfile

__Изменение кода инфраструктуры по сути выполняется так же как разработка. Создается ветка, правки и потом МР__

## Pipeline и jobs
__pipeline - Это по сути инструкция к выполнению, которая состоит из этапов. Все что описано в пайплайне будет выполняться друг за другои последовательно. Джобы на разных этапах могут выполняться параллельно.__
__Пример стандартного пайплайна (CI):__
1) Компиляция кода
2) Тесты
3) Проверка безопасности
4) Сборка в образ
5) Отправка в registry

__Артефакт - результат работы джобы. Может передавать между джобами. Так же могут кешироваться зависимости чтоб каждый раз их не скачивать.__
__Триггеры CI/CD:__
1) push
2) merge
3) Крон команда
4) Внешний запрос (Вебхук)
5) Ручной запуск
6) Создание тега


## GitHab Actions

__GitHab actions - это встроенна в Гитхаб система автоматизации. Работает по прицнипу воркфлоу.__

__Воркфлоу - это файлы в формате yaml (yml). Они описывают автоматизацию__

__Воркфлоу сосостоят из джоб (jobs), которые выполняются на вирт машинах(runners).__

__Так в же в Github есть свой маркет. Там выкладывают просто заранее подготовленные действия__

__Является отдельным продуктом__

## GitLab CI/CD

__Сразу встроен в GitLab. Так же использует раннеры. Типы раннеров:__
1) Shared - предоставляют гитлабом с лимитами - Контролируются самим гитлабом
2) Group - Доступные всем проектам в группе - Личный раннер запущенный на своем сервере 
3) Specific - Доступные для конкретного проекта - Личный раннер запущенный на своем сервере 

__Gitlab имеет встроенную поддержку окружений__
__Так же может создавать изолированную среду для МР. Позволяет тестить прилу до мержа.__

## Jenkins

__Jenkins - популярный CI/CD сервер.__
__Используется архитектура master-agent. Мастер дает указание агент выполняет. С помощью этого сборки могут быть изолированы друг от друга, можно использовать разные ОС, можно экономмить ресурсы__


## Стратегия ветвления и CI/CD

__Стратегия ветвления влияет и на настройку CI/CD. Например для Git flow для каждого типа ветки настраивается отдельно правила, что как проверяется.__
__Для GitHub Flow - на фича ветках запускаются тесты и тд. При мерже в main может запускать сразу деплой в прод__
__Для Trunk-based development - часть фокус на быстром деплое и откате.__

## Секреты и безопасность

__Секреты не должны хранится в репозитории. По большей части они хранятся в переменных окружения. Так же разграничивают доступ для Job. Каждая джба имеет доступ только к тем данным, которые ей нужны дял выполнения.__

## Мониторинг

__При запуске сборок есть куча метрик и некоторые из них стоит отслеживать. Например время сборки, время раскатки от запуска до прода, процент успешных сборок, время фикса битой сборки. Это помогает улучшать процесс делая его быстрым и эффективным.__
__Так же CI/CD позволяет отправлять метрики в мониторинг типо прометуса, графаны и тд. Помогает настроить алерты, чтобы быстрее реагировать на проблемы.__

## Оптимизация CI/CD

__Есть подходы для оптимизации CI/CD процессов:__
1) Параллельные запуски - вместо последовательного запуска тестов, линтера и тд можно запускать параллельно (Только для независимых задач).
2) Инкрементальные сборки - собираем только измененное (Например брать ранее скомпилированные файлы, если они не менялись/ СОбирать только измененный микросервис)
3) CI/CD кешировние - кешировать переменные, результаты тестов, промежуточные файлы
4) Fail fast - амые быстрые проверки идут первыми. Ненужно ждать тестов если упал линтер

# Типовые проблемы

__Git почти все запоминает и хранит, так что в большинстве случае даже если что то сломалось, это можно восстановить. Сборщик мусора сносит коммиты не моложе 2 недель.__

__Перед исправлением, нужно понять что именно произошло. Понимание как git хранит данные помогает в этом разобраться. Только после понимания, можно чинить__

## Проблемы с коммитами

### Коммит запушен не в ту ветку

__Бывает что не переключился на нужную ветку. Сначала нужно посмотреть, что коммит реально ушел не туда. Надо посмотреть последние коммиты через git log. Если коммит там есть, то проблема подтерждена. Тут иожно перенести черри пиком в нужную ветку, а в текущей сделать reset. Если коммит ушел в удаленный репозиторий, то так же черри пик а для ветки в которую ушел сделать revert.__

### Неправильное сообщение коммита

__Опять же смотрим через git log. Если сообщение кривое и коммит локальный, делаем --amend. Если ушел в удаленный репозиторий, то тут лучше ниче не трогать.__

### Потерянные коммиты через reset

__Сделал reset и снес больше чем нужно. Тут через reflog находишь хеш коммита нужного и так же через reset на него указываешь. ресет по сути просто указывает де новый последний коммит для ветки__

## Проблемы с ветками

### Удаленная ветка исчезла из удаленного репозитория

__git remote prune origin --dry-run - покажет какие ветки удалены на сервере, но есть локально. После этого можно выполнить git fetch --prune или тот же git remote prune origin__

### Ветки разошлись 

__git push может выдать ошибку тк появились новые коммиты в удаленном репозитории. Тут делаем git fetch + git merge <ветка удаленного отслеживания> и потом пушим, либо git pull --rebase или просто, а потом снова пушим. Если конфликты есть, то решаем__

### Попали в состояние detached HEAD

__Такое бывает если HEAD указывает прям в коммит, а не на ветку. Если не делали коммитов, то переключаемся, если делали, то в текущем положении создаем ветку и коммиыт будут уже в ней__

## Проблемы с merge и коммитами

### Конфликты при мерже

__Анализируем конфликт. Выбираем нужную версию или свою делаем. Убираем маркеры. Тестим. Добавляем в индекс. Дальше от способа зависит, либо пушим, либо через --continue__

### Прерванный merge

__Увидел сложные конфликты и хочш отменить полностью мерж. Делает --abort__

## Проблемы с удаленным репозиторием

### Ошибка аутентификации

__Есть есть проблема с аутентификацией сначала проверяем ссылку на репозиторий тот ли git remote -v. Проверить что токен есть на сервере хостинге (Гитлаб например). Проверь что запущен например агент и в нем есть ключ приватный__

### Ошибка при пуше больших файлов

__Сервера хостинги имею ограничение, так что можно получить отказ пуша. Проблема в том, что файл уже в истории. Через git reset отвязываемся от последнего коммита.__

### Превышен лимит размера репозитория

__Тут система может не принимать пуш. Надо архивировать старые ветки/удалять с истории коммиты с большими файлами__

## Проблемы производительности

### Медленные операции git

__Такое может произойти, если история большая или веток много или файлы в истории большие. Тут можно часть кешировать, можно оптимизировать через команды__

### Медленное клонирование

__Тоже проблема может быть из за большого репозитория. Можно клонировать указывая depth или конкретные ветки через --branch и --single-branch.__

### Файлы не отслеживаются

__Изменил файл, а он не отслеживается. Тут надо посмотреть нет ли его в .gitignore. Не бинарный ли файл? Есть ли доступы?__

### Файлы постоянно помечаются измененными, хотя их не трогали

__такое бывает при работате между Windows и Unix подобными системами. Нужно правильтно настроить git: git config core.autocrlf true на Windows, false на Unix__

## Критические проблемы

### Git выдает ошибку о поврежденных файлах

__Попробовать подтянуть с удаленного репозитория коммиты. Удалить пустые файлы в папке objects. В крайнем случае репозиторий переклонировать__

### Случайно запушили се креды

__Удалить из истории этот коммит. Сообщить в ИБ что данные скомпроментированы. force push очищенной истории. Сказать всем что надо репу переклонировать или актуализировать с актуальной веткой.__

## Инструменты диагностики

### git fsck - проверяет целостность бд git. Помогает найти битые файлы.
### git reflog - история всех изменений HEAD
### git blame - показывает кто и когда изменил каждую строку кода.

__Чтобы превентировать проблемы нужно соблюдать практики:__
1) Регулярные бекапы
2) Добавление подтверждений для опасных команд
3) Обучение команды
4) Код ревью
5) Документация процессов работы над репозиторием
